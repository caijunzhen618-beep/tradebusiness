# 核心 V1 重写 vs 基于 V0 改造决策

## 1. 结论

选择：**核心 V1 领域重写，选择性复用 V0 工程基础设施；V0 并行保留，不做全仓推倒重来。**

这里的“重写”只针对获客核心领域：物流产品、全局企业事实库、联系人/联系方式、Evidence、产品匹配、产品潜客池、联系活动、补客流水线。身份、用户、邮件发送、通知、文件、计费、日志、数据库/Celery 部署骨架按评估复用。

## 2. 两条路线比较

评分：1=差/高风险，5=好/低风险。

| 维度 | 基于 V0 改造 | 核心 V1 重写 | 判断 |
| --- | ---: | ---: | --- |
| 首个页面/接口表面交付 | 4 | 3 | V0 改字段短期看似更快 |
| 完整 V1 总开发成本 | 2 | 4 | V0 三套线索模型的持续兼容和修补成本高 |
| 技术债 | 1 | 4 | Lead task 私有、Customer 单表、永久 score/status 与 V1 根冲突 |
| 数据迁移可控性 | 2 | 4 | 原表原地改造难回滚；新表 ETL 可演练/对账 |
| 上线风险 | 2 | 4 | 原地改会同时影响 V0；旁路 V1 可灰度 |
| 可维护性 | 2 | 5 | V1 对象与业务术语一一对应 |
| 企业跨产品复用 | 1 | 5 | V0 task_id Lead 天然制造重复 |
| Provider 扩展性 | 2 | 5 | V0 scraper/task 强耦合；V1 contract 可替换 |
| 未来跨行业底座 | 2 | 4 | V1 通用事实库不绑定货代字段 |
| 回滚能力 | 2 | 5 | 新表/新 API 可按流量切回 V0 |
| **合计** | **20/50** | **43/50** | 选择核心重写 |

## 3. 为什么不是在 Lead/Customer 上继续加字段

这不是命名问题，而是数据所有权问题：

- V0 `Lead.task_id` 把企业所有权放在一次搜索任务，V1 要求企业全局唯一、跨产品复用。
- V0 `Customer` 把电话、邮箱、线路、客户状态塞在一行，V1 要求多个联系人、多个联系方式、逐点有效性和带来源 Evidence。
- V0 `match_score` 是永久数值，V1 要求可解释、动态组合、可追溯推荐理由。
- V0 Lead 的 `status/do_not_contact` 是企业/Lead 全局状态，V1 联系结论属于产品 × 角色语境，拒绝还分产品与企业全局。
- V0 的搜索任务让用户配置国家、行业、关键词和排除词，V1 明确由系统根据物流产品和客户角色生成策略。

若原地改造，需要长期同时解释新旧字段、同步三套表并修补每个查询口径，最终成本高于建立清晰的新核心。

## 4. 成本与风险控制

### 核心重写的真实成本

- 新建约 16 张业务表、V1 API、领域 Service/Repository、前端工作台和异步编排。
- 编写迁移脚本、对账工具和双轨灰度。
- Provider 的真实产出率未知，需要先做技术验证。

### 降低风险的办法

- Strangler 模式：`/api/v1` 下新增清晰资源路由（必要时内部以 feature flag 区分），V0 页面/API 不删除。
- 先完成 schema/契约/假 Provider 的竖切，再接真实 Provider。
- 迁移先 dry-run，按企业合并置信度分自动/人工；任何阶段不覆盖 V0。
- 将 product matching 做成可重建投影，规则错误可改版本后重算。
- AcquisitionRun 数据库持久化，每批幂等，避免 worker 重启造成重复企业/重复扣费。

## 5. 数据迁移决策

V0 数据按“可证明才迁移”处理：

- Customer/Lead/ScrapedLead 共同进入实体解析，不按原 ID 直接一对一生成 Prospect。
- LeadContact 拆成 Contact + ContactPoint。
- source/source_url/raw_sources 生成 ProviderRecord/Evidence；无来源总结不用于 V1 准入。
- 旧 match_score 不迁移。
- 联系/邮件历史尽可能关联到 Prospect；无法确定产品语境时标记 `legacy_unscoped`，不推导某产品业务结论。
- V0 DNC 进入人工复核，只有明确企业全局拒绝证据才升级为 global suppression。

## 6. 决策触发的实施边界

技术方案确认前只允许：需求/原型/架构文档、数据探查、Provider spike、迁移 dry-run、API 契约草案和测试设计。不得创建正式 V1 业务表、接生产流量或开发正式业务实现。

技术评审确认后，以 ADR 固化：表结构、租户边界、Provider 合规与首批接入、队列幂等、迁移阈值和灰度方案。
