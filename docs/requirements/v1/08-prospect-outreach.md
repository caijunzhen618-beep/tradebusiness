# V1-08 潜客触达与最小跟进闭环【已确认】

> 状态：已确认  
> 版本：V1  
> 当前范围：国内拓客第一阶段，不扩展为完整 CRM、报价、订单或成交系统。

## 1. 业务目标

业务员拿到产品潜客池后，完成最小闭环：

```text
查看潜客
  ↓
电话 / Email 触达
  ↓
记录联系结果
  ↓
必要时设置下次跟进
  ↓
销售确认的业务事实反哺企业事实库
```

国内场景第一版遵循：有手机/电话则支持业务员打电话，有邮箱则支持邮件触达。两个都有时同时展示，由业务员自行决定渠道。

## 2. 第一版触达渠道

- `phone`：电话/手机
- `email`：邮件

第一版不要求集成系统内电话拨号。手机号、电话、邮箱至少支持一键复制；Email 可以复用现有邮件发送能力并逐步优化。

微信、拜访、WhatsApp 等渠道待真实业务验证后再扩展，不提前穷举。

## 3. 联系结果【已确认】

一次触达后只要求业务员选择一个简洁结果：

| 结果 | 业务含义 | 处理原则 |
| --- | --- | --- |
| 未联系上 | 无人接、暂时没找到人等 | 保留，可后续再次联系 |
| 无该方向业务 | 对方明确没有当前物流产品对应方向的业务 | 当前产品下暂不优先 |
| 有该方向业务，暂无货 | 确认存在该方向业务，但当前没有货 | 有效潜客，值得后续维护 |
| 近期有货 / 可以询价 | 已出现实际物流机会 | 重点跟进 |
| 联系方式无效 | 空号、错邮箱、找错联系方式等 | 更新对应 ContactPoint 有效性 |
| 拒绝联系 | 对方明确不希望继续开发 | 后续停止该类触达 |

第一版不使用 MQL / SQL / Qualified / Converted 等通用 CRM 术语。

## 4. 为什么“无业务”和“暂无货”必须分开

“我们不做委内瑞拉”和“我们做委内瑞拉，但最近没有货”业务价值完全不同。

后者已经由销售确认该企业确实存在目标方向业务，是高价值第一方数据，不能归为普通无需求。

同样，“当前没有货”不能被错误写成“没有该方向业务”。

## 5. ContactActivity

每次触达保存客观历史：

```text
ContactActivity
- id
- prospect_id
- product_id
- contact_id?          # 可空
- contact_point_id?    # 可空
- channel              # phone / email
- occurred_at
- result
- note?                # 可空
- next_follow_up_at?   # 可空
- created_by
- created_at
```

电话/邮件是触达渠道；`result` 才是本次业务结果。二者不能混为客户状态。

## 6. 跟进保持最小化

当结果为“近期有货/可以询价”或业务员认为需要继续跟进时，仅要求可选填写：
- 下次跟进时间
- 备注

例如：

> 有一票汽配，约 8 方，广州出，让我明天报价格。

第一版不因此自动扩展完整 Opportunity / Quote / Order 模型。真实询价、报价、成交链路后续根据实际业务再设计。

## 7. 联系结果是产品级业务结论

同一家企业可能：
- 委内瑞拉：有业务，暂无货
- 韩国：近期有货
- 南非：无相关业务

因此不能在 Prospect 上设置一个全局 `status=interested`。

联系历史必须关联 `prospect_id + product_id`。产品潜客关系与 ContactActivity 共同表达企业在某个物流产品下的真实销售验证情况。

## 8. 销售反馈反哺企业事实库

业务员电话/邮件确认的事实比纯公开网络推测更有价值。

例如业务员确认：

> ABC 国际物流确实有委内瑞拉方向业务。

系统应形成可复用的第一方 Evidence，例如：

```text
prospect_id = ABC
type = destination_business
country_code = VE
source_type = sales_verified
```

该事实以后可以提高 ABC 对委内瑞拉相关产品的优先级，并被其他合适产品复用。

销售反馈也必须保留时间和来源，避免把历史业务事实当成永久不变事实。

## 9. 联系方式无效反馈

如果业务员确认某电话为空号、某邮箱错误：
- 不删除 ContactPoint 历史；
- 将 `is_valid=false`；
- 后续可用潜客判断和排序不再依赖该无效联系方式；
- 数据可用于评估来源质量。

## 10. ProductProspect 不重复保存可计算状态

第一版 ProductProspect 仍保持轻量：

```text
ProductProspect
- id
- product_id
- prospect_id
- added_at
```

`last_contact_at`、`last_result`、`next_follow_up_at` 等如果可以从 ContactActivity 计算，则不重复存储，遵循“能从已有数据计算的信息不额外维护状态”的原则。

## 11. 潜客列表第一版重点信息

业务员查看某产品潜客时，优先看到：
- 公司名称
- 推荐理由 / Evidence 摘要
- 具体联系人及职位（如有）
- 手机 / 电话 / Email
- 一键复制/邮件触达入口
- 最近联系结果（如有）
- 下次跟进时间（如有）
- 记录联系结果入口

目标是让业务员可以连续处理潜客，不要求每次触达后填写复杂 CRM 表单。
