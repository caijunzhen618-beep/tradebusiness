# V1-09 产品边界与可复用底座原则【已确认】

> 状态：已确认  
> 版本：V1

## 1. 当前产品仍然只做货代国内拓客

V1 不因为底层能力具有通用性，就把用户体验改造成通用 B2B 获客平台。

当前产品继续围绕货代真实语言与业务规则设计：
- 物流产品 / 优势线路
- 目的国家
- 国内同行货代
- 出口货主
- 同行资源互补/庄家识别
- 出口市场 Evidence

目标是让货代用户尽量只表达“我卖什么、我要找哪类客户”，系统承担搜索策略与数据处理复杂度。

## 2. 底层能力尽量行业无关

以下核心能力应避免不必要地绑定货代专属字段：
- Prospect 企业事实库
- Contact
- ContactPoint
- Evidence
- 企业识别与去重
- Company Enrichment
- 数据源 Provider
- Product/Offering Matching
- 潜客库存
- ContactActivity
- 销售反馈 Evidence

例如 Prospect 不直接塞 freight_route、shipping_port 等货代专属字段。货代领域事实通过 LogisticsProduct、Evidence 和领域策略表达。

## 3. “通用底座 + 货代策略”

概念上：

```text
通用企业获客底座
├─ 企业事实库
├─ 联系人/联系方式
├─ Evidence
├─ 数据源 Provider
├─ 匹配
├─ 潜客库存
└─ 触达反馈
        ↓
货代领域策略
├─ LogisticsProduct
├─ 目的国/区域理解
├─ 同行发现策略
├─ 出口货主发现策略
├─ 同行庄家/互补判断
└─ 货代相关 Evidence 解释
```

V1 只交付货代领域产品，不在用户界面暴露“行业策略包”等抽象概念。

## 4. 为什么暂不做通用产品

如果过早通用化，系统容易重新要求用户配置客户画像、关键词、排除词、评分规则等复杂参数，退化成通用搜索/AI 获客工具。

货代垂直价值恰恰来自系统能够理解“委内瑞拉海派双清”并自动知道同行与出口货主要采用不同发现、准入和排序逻辑。

## 5. 未来扩展原则

如果货代场景验证成功，未来可以将 LogisticsProduct 抽象为 Offering，并新增其他行业策略，而无需推翻企业事实库、联系人、Evidence、Provider、匹配和触达反馈等底层能力。

该扩展属于未来可能性，不进入当前 V1 功能范围和验收标准。
