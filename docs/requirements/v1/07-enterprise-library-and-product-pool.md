# V1-07 企业库、产品匹配与产品潜客池【已确认】

> 状态：已确认  
> 版本：V1

## 1. 不是“每个产品一张潜客表”

全系统维护一份共享的企业事实库。不同物流产品通过关系数据引用企业，不复制 Prospect、Contact、ContactPoint。

错误设计：
- 委内瑞拉潜客表复制一份 ABC 公司
- 韩国潜客表再复制一份 ABC 公司

正确设计：

```text
Prospect 全局企业库
        │
      ABC公司
        │
   ┌────┴────┐
   ↓         ↓
委内瑞拉产品  韩国产品
```

## 2. 三层模型

### 第一层：企业事实库
回答：**这家公司是谁、它有什么客观业务事实、怎么联系？**

主要对象：
- Prospect
- Contact
- ContactPoint
- 企业级 Evidence

### 第二层：产品匹配
回答：**这家企业对于某个物流产品是否值得作为候选，以及为什么？**

匹配尽量通过企业事实 + LogisticsProduct 动态计算，不重复抓取企业基础数据。

### 第三层：产品潜客池
回答：**业务员当前针对这个物流产品实际准备处理哪些企业？**

产品潜客池是业务工作集，不是独立企业数据库。

## 3. ProductProspect 关系

建议使用关系对象表达某企业进入某物流产品潜客池：

```text
ProductProspect
- id
- product_id
- prospect_id
- added_at
```

第一版不在该关系上保存永久 Match Score。推荐理由和排序通过 Evidence、联系方式及当前规则动态计算。

同一 Prospect 可以同时拥有多个 ProductProspect 关系，但企业基础数据只维护一份。

## 4. 企业库复用场景

第一次为“委内瑞拉海派双清”获客时发现 A 企业，并富化得到：
- export_market = VE
- export_market = KR
- export_market = JP
- 联系人与电话/邮箱

以后创建“韩国海派双清”时，系统直接复用 A 的企业与联系方式数据，并根据 KR Evidence 判断其为韩国产品候选，不需要重新抓 A 的官网。

## 5. 新企业反向增强旧产品

假设后来为韩国产品获客，新发现 D 企业，并同时获得 Korea + Venezuela 市场事实。

D 写入全局企业库后，Product Matching 会发现：D 也适合委内瑞拉产品。

系统不需要立即重新跑委内瑞拉互联网搜索，也不强制自动把 D 加入委内瑞拉业务池；当用户下次为委内瑞拉产品补充潜客时，D 应成为优先可复用候选。

## 6. 产品潜客池不是企业库的全部视图

一个普通出口企业不能因为全局存在就自动出现在所有物流产品潜客池中。

企业库负责共享数据资产；ProductProspect 表示企业已经进入某产品的实际业务工作集。新增产品时，应先从企业库匹配高/中相关候选，再按需要逐层扩展和外部发现。

## 7. 补池优先级

当产品潜客池存在缺口时：
1. 优先使用企业库中新出现且与该产品强/中相关的候选；
2. 再使用企业库中其他符合准入条件的合格企业；
3. 仍不足才启动该产品的增量外部发现；
4. 新发现企业完整富化后进入全局库，同时反向增强其他现有产品的候选集合。

## 8. 数据资产效果

随着系统使用时间增加：
- 企业库规模增加；
- 每个企业的市场/业务/联系方式 Evidence 更丰富；
- 新产品创建时企业库直接命中率提高；
- 老产品补池也可以消费其他产品搜索过程中新增的匹配企业；
- 外部重复搜索和联系人重复获取成本下降。

这使系统从“每个产品反复搜索互联网的工具”逐步变成“不断积累企业事实、可被多个物流产品复用的获客数据资产系统”。
