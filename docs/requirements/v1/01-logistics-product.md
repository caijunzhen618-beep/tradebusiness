# V1-01 物流产品【已确认】

> 状态：已确认  
> 版本：V1  
> 当前产品边界：国内拓客。系统帮助国内货代在中国境内发现潜在客户企业并获取可触达联系方式。

## 1. 设计目标

物流产品在本系统中的作用不是完整描述货代履约能力，而是给获客引擎提供“我卖什么”的必要信息。

设计判断标准：**只有会影响“应该找谁”的信息，才优先结构化。** 报价、订舱、港口操作、清关履约等需要的信息，不因为货代业务本身复杂就提前塞入获客产品模型。

例如用户可以维护：
- 委内瑞拉海派双清
- 南非海派双清
- 韩国海派包税

但对于当前国内获客，双清、包税、末端派送、起运港、揽收范围等尚未证明会显著改变第一阶段潜在客户池，因此 V1 第一版不作为核心结构化搜索字段。

## 2. 字段

| 字段 | 必填 | 类型 | 示例 | 作用 |
| --- | --- | --- | --- | --- |
| product_name | 是 | 文本 | 委内瑞拉海派双清 | 产品展示名称 |
| destination_country | 是 | Country 标准字典 | VE / 委内瑞拉 | 核心获客特征 |
| transport_mode | 是 | 单选枚举 | sea | 核心获客/搜索扩展特征 |
| description | 否 | 文本 | 双清到门，全国可接等 | 保留业务员希望描述的其他产品能力，不要求结构化 |
| status | 是 | 单选枚举 | active | 产品是否继续使用 |
| created_at | 系统 | 时间 | - | 审计字段 |
| updated_at | 系统 | 时间 | - | 审计字段 |

当前国内拓客场景的起运国家默认为中国，不要求用户创建产品时重复填写 `origin_country`。

## 3. 枚举

### transport_mode
- `sea`：海运
- `air`：空运
- `rail`：铁路
- `road`：陆运
- `multimodal`：多式联运

### status
- `active`：启用
- `inactive`：停用

国家不做普通业务枚举，使用标准 Country 字典（建议 ISO 国家代码）。

## 4. 产品名称规则

产品名称采用：**系统可根据结构化信息给出默认名称，用户允许修改。**

产品名称主要用于展示和符合货代日常业务叫法，例如“委内瑞拉海派双清”“韩国海派包税”。即使用户修改名称，获客引擎仍优先使用 `destination_country`、`transport_mode` 等结构化字段，而不是只依赖名称字符串判断。

## 5. 第一版明确不结构化的能力

以下字段从此前 V1-01 核心模型移除：
- origin_country：当前场景系统默认中国
- load_types：LCL/FCL/parcel
- pickup_regions
- origin_ports
- destination_ports
- delivery_regions
- export_customs
- import_customs
- last_mile_delivery
- tax_mode
- cargo_notes / accepted_cargo

删除原因不是这些信息在货代业务中不重要，而是**当前没有证据表明它们会明显改变国内第一阶段潜在客户发现结果**。如果后续验证某字段会改变目标客户池或搜索策略，再升级为结构化字段。

其中“双清、包税、到门、特殊货能力”等可以先体现在 `product_name` 和 `description` 中。

## 6. 明确不属于物流产品

以下内容属于其他业务对象：
- 客户类型（同行货代 / 工厂）
- 客户地区
- 搜索关键词与排除词
- 搜索数据源
- 潜客池目标数量
- 客户匹配/相关性
- 联系方式
- 联系与跟进状态

## 7. 当前确认的获客使用方式

对于国内同行发现，物流产品的 `destination_country + transport_mode` 用于扩展搜索和相关性判断，但不作为硬过滤条件。

例如“委内瑞拉海运”既可以驱动基础国际货代发现，也可以扩展“委内瑞拉 / Venezuela / 拉美 / 南美 + 货代/海运”等产品相关搜索。一个官网没有写委内瑞拉的国际货代仍然可能是潜在客户。

## 8. 待后续验证

工厂客户的发现逻辑尚未讨论完成。待工厂发现规则确认后，再反向检查物流产品是否还需要增加对获客真正有价值的结构化字段。
